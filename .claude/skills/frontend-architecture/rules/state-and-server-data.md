(derive-don't-store, `useEffect` misuse, context re-render costs) belongs to
`react-best-practices`. This file covers only **placement**.

## Classify the state first

| Kind | Example | Lives in | Source |
|---|---|---|---|
| Server cache | Lists, entities, run results | Data-fetching library cache (TanStack Query, SWR), via API-layer hooks | [S8] [S27] [S28] |
| Component UI state | Open/closed, hovered tab, input draft | `useState`/`useReducer` in the lowest component that needs it | [S8] [S14] |
| Shared UI state | Values two siblings need | Closest common parent, passed down (lift state up) | [S16] [S20] |
| App-wide UI state | Theme, toasts, current workspace | Context provider (or a store), as deep in the tree as possible | [S2] [S8] [S27] |
| Form state | Field values, validation | Form library, or local state, with a schema validator | [S8] |
| URL state | Filters, pagination, selected tab worth sharing | Route params / search params | [S8] |

Server cache and UI state need different tools. Keeping them apart removes most of the demand
for a global store [S27].

## Server cache

- Never copy query data into `useState`. The copy stops receiving background updates [S28].
- Wrap each endpoint in a custom hook in the API layer, so components never build query keys
  or call fetchers themselves [S7] [S28].
- Keep query keys next to the queries in each feature, generated by a key factory and ordered
  from generic to specific (`['todos', 'list', { filters }]`). That makes invalidation at any
  level easy [S29].
- With TanStack Query v5, define key + fn once with `queryOptions` and reuse it in `useQuery`,
  prefetching and `getQueryData` [S30].
- Mutations invalidate the key prefixes they affect. The invalidation lives in the mutation
  hook, not in components.

## UI state

- Give every piece of state one owner, a single source of truth. Lift it to the closest
  common parent when two components must stay in sync [S20].
- Keep the state structure minimal: no redundant, contradictory or duplicated fields; store
  IDs and derive the rest [S19].
- Choose context for app-wide concerns only. Render providers as deep in the tree as
  possible [S2].

## Next.js with a client data cache

- Give each piece of data one owner: either it is rendered by a Server Component, or it is
  fetched by a client query. When a Server Component renders query data, the query library
  can't revalidate it, and the two copies drift [S31].
- When prefetching on the server, create a new QueryClient per request on the server and use
  a single instance in the browser, then pass data through `HydrationBoundary` [S31].
- For a new Server Components app, consider the framework's own data fetching before adding a
  client cache. A client cache fits apps that fetch from a separate backend in the browser
  [S31].
